# AegisDB v0.9.0 — setting it up, and knowing that it worked 🩺

**Minor bump, entirely additive.** No migration, no format change, no
behavioural change to any existing operation. The theme is the distance between
"I installed AegisDB" and "my agent is actually remembering things", which was
longer than it needed to be and — worse — silent when it failed.

Almost every way this integration breaks is quiet. A dimension that disagrees
with the server refuses every embedded write. A hook missing from
`settings.json` recalls nothing and says nothing. `AEGIS_ASK_PATTERN` with no
extraction backend answers every question by ordinary search. None of those
raise, none appear in a transcript, and each leaves the setup looking finished.

## Install the integration without a clone

```
/plugin marketplace add d4n-larsson/aegisdb
/plugin install aegisdb-memory@aegisdb
```

Then, in any project you want to give a memory:

```
/aegis-setup     # a few short questions, then it scaffolds this project
/aegis-doctor    # check the wiring whenever recall looks wrong
```

Until now the guided skill had to be copied out of a git checkout, directly
beside a zero-clone `uvx` story for everything else.

The plugin ships **only** the skill and the check. The memory server
registration and the recall/capture hooks stay per-project, written by
`aegisdb-init`, because they are a per-project decision — which server, which
namespace, which embeddings — and because a plugin registering them globally
would collide with the ones the scaffolder writes: two `memory` servers, and
hooks firing twice, recalling twice into one turn and capturing the same session
twice.

## `aegisdb-doctor`

```text
✓ config      /repo/.aegisdb/config.json (discovered)
✓ namespace   my-project-6a9dbcb9
✓ server      127.0.0.1:9470 v0.9.0 phase 4
✗ dimension   client 384 ≠ server 1024 — every embedded write is refused
              → set embedding_dimensions to 1024, or restart the server with --embedding-dim 384
✓ mcp entry   `memory` registered in .mcp.json
✓ hooks       recall + capture wired in .claude/settings.json
✗ read path   AEGIS_ASK_PATTERN is set but AEGIS_EXTRACT_MODE is 'none'
              → every question falls back to ordinary search, answering "symbolic": false
✓ round trip  saved, found and removed record 41
```

One command over every link between a project and its memory, ending in a real
`save → search → delete` — the only check that proves the chain, since all the
others can pass on a server the project cannot actually write to. Every failure
names its fix. Exits non-zero, so a pre-commit hook or a CI step can run it;
`--json` for scripts; `--no-write` to skip the round trip.

The distinctions are the point: a server that is *down* reads differently from
one too old to report its dimension, a missing `.mcp.json` differently from an
unparseable one, a missing package differently from a missing API key. One
outage reports as one failure, not a column of red.

## `ping` now reports the server's embedding dimension

```json
{ "ok": true, "version": "0.9.0", "phase": 4, "embedding_dimensions": 1024 }
```

The one setting a client was **told** rather than able to check. Every vector a
client sends has to match `--embedding-dim`, and a client keeping its own copy of
that number keeps a copy that can drift — the mismatch then survives setup and
first appears as a refused write, long after anyone would connect it to a flag on
another machine. Reported by `ping` rather than `stats` because the client that
most needs it is one being configured, which has no token yet; `ping` is exempt
from authentication and a dimension is not a secret. Same move `predicates` made
for the vocabulary: ask the server instead of keeping a second copy of what it
enforces.

Which means the integration stops asking you for it:

- **`aegisdb-init` reads it** instead of defaulting to 1024/384, and warns rather
  than silently writing a value that disagrees.
- **The MCP server warns at startup** instead of waiting for the first refused
  write.
- **`aegisdb-doctor` checks the two still agree.**

## `aegisdb-init --start-local`

```bash
uvx --from aegisdb-mcp aegisdb-init --start-local
```

The scaffolder used to write a perfect client config and then say *"unreachable
— start the server, then re-run"*, leaving the one step it could have taken. It
now starts a named container (`aegisdb`) on a named volume (`aegis-data`), waits
until the server **answers a ping** rather than until Docker returns — a
container runs while the server is still opening its data directory — and reads
the dimension back from it. Interactively you are offered this whenever nothing
is listening, so the flag need not be known.

It **adopts** an existing `aegisdb` container rather than racing it for the port,
and if that container turns out to be mapped to a different port it says so and
names `docker port`, rather than timing out and sending you to read the logs of a
perfectly healthy server.

## Operator notes

- **Nothing to migrate.** No new file in the data directory, no format change,
  no flag to set. `embedding_dimensions` is an added response field; a client
  that ignores it behaves exactly as before.
- **Old client, new server** is fine, and **new client, old server** degrades
  honestly: the field is absent, and absent means *unknown*, never zero. The
  doctor reports the dimension check as unverifiable rather than failing it.
- **`--start-local` is guarded**, because starting a container is a side effect
  on the machine: never on `--yes` alone (that means "don't ask me about the
  config"), never under `--print`, and refused for a non-local `--host` —
  binding a container here and pointing the project at another machine is two
  wrong things that look like one working setup.
- **The doctor's round trip writes.** It saves one record tagged
  `aegisdb-doctor`, finds it and deletes it. Use `--no-write` on a store where
  even a transient record is unwelcome.
