# AegisDB v0.8.1 — one place a project's memory settings live 📁

**Integration-only.** The server, the wire protocol, the on-disk format and the
`aegisdb` client SDK are unchanged from v0.8.0; the image is republished at the
new tag carrying the same code. Everything here is `aegisdb-mcp`, the Claude
Code memory integration.

The theme is settings that reach *both* callers. The MCP server gets its
environment from `.mcp.json`, but a Claude Code hook entry has **no env field at
all** — so a project configured for `embedding_mode: local` on the server was
still recalling *without* embeddings in the hook, silently, because the hook fell
back to the built-in defaults. A file on disk is read by whoever runs next.

## `.aegisdb/` — the project's own directory

`aegisdb-init` now scaffolds one place for everything the integration reads from
or writes into your project:

```text
.aegisdb/
  config.json      # settings both the MCP server and the hooks read — commit this
  predicates.json  # your predicate vocabulary — starter copy written for you
  facts/           # typed-fact corpora, loaded by `aegisdb-seed` — commit these
  local/           # machine state: gitignored wholesale, never committed
```

The split is the point: everything beside `local/` is a reviewed input that
belongs in git — the namespace this project writes under, the vocabulary it may
assert in — and `local/` is machine state that does not. One gitignore line,
which `aegisdb-init` adds, and no per-file judgement calls.

`config.json` is **discovered, not configured**: `AEGIS_CONFIG` still names a
file explicitly and always wins, but with it unset the project's
`.aegisdb/config.json` is read if present. Precedence is unchanged — defaults →
file → environment → explicit overrides — so the file loses to the environment
the way every other source does.

Two things deliberately not in it: the **auth token**, because this file is
meant to be committed and a bearer token in git is a different class of mistake
than a wrong port; and the **server's data directory**, which stays wherever you
point `--data-dir`.

### The namespace is now pinned

With no namespace configured the fallback is `basename(project) +
hash(absolute path)` — stable until someone renames or moves the directory, at
which point everything written under the old name becomes unreachable.
`aegisdb-init` now writes the value it *already* resolves to into `config.json`:
a no-op for an existing project, and a fix for a future move.

### `aegisdb-seed`

```sh
aegisdb-seed --dry-run    # report what would be written
aegisdb-seed
```

Loads a project's typed-fact corpora, discovering everything from `.aegisdb/`
rather than taking it as arguments — so a corpus lands in the namespace the agent
recalls from instead of one somebody typed twice. Two passes, because a fact
names its subject and object by record id and those ids do not exist until the
entity records are written; the corpus refers to them by label. Idempotent: an
entity whose exact prose already exists is reused and a fact already asserted is
skipped, so the useful loop — run it, read the result, adjust the corpus, run it
again — does not double the store.

## Behavioural change: a *named* config file that is missing is now an error

`AEGIS_CONFIG` pointing at a path that is not there used to be treated exactly
like a discovered `.aegisdb/config.json` that is simply absent: silent defaults.

```
[aegis-mcp] config: AEGIS_CONFIG names /repo/.aegisdb/config.json, which does not exist
```

Naming a path is a claim that it is there, so its absence is a
misconfiguration — and the failure the silence causes is the precise one this
file exists to prevent: settings reverting to the built-ins with nothing said,
`embedding_mode` back to `none`, recall still working and quietly retrieving
worse. A *discovered* file that is absent stays normal and still means
"defaults".

**Where this can bite:** if `AEGIS_CONFIG` points into a working tree while
`.aegisdb/` exists on only some branches, the MCP server will now refuse to start
on the branches without it rather than reconfiguring itself silently. Unset
`AEGIS_CONFIG` and let discovery find the file, or point it somewhere every
checkout has. The hooks already catch everything and degrade to a no-op with the
message on stderr; `aegisdb-mcp`, `aegisdb-summarize` and `aegisdb-seed` print
the sentence rather than a traceback.

## `ask_pattern` says why it is not answering

`AEGIS_ASK_PATTERN=true` with `AEGIS_EXTRACT_MODE` at its default `none` does
nothing at all: expressing a question as a `pattern` is a *model* call, so the
read path runs on the extraction backend, and with none available every question
falls back to ordinary search.

The additive design is what made that invisible. A read path that never ran and a
question the corpus cannot answer both come back `"symbolic": false`, and the
line separating them went to stderr — which belongs to whoever launched the
server, not whoever is asking. So the reason now travels with the result:

```json
{ "ok": true, "symbolic": false, "memories": [ … ],
  "read_path": "AEGIS_ASK_PATTERN is set but AEGIS_EXTRACT_MODE is 'none' — …" }
```

`read_path` appears only when the read path is configured and cannot run, and
only on the unfiltered questions it would have taken. It is **absent when the
feature is off and when it is working**, so a store that does not use it is
byte-identical to v0.8.0.

Startup now says it in both directions — `read path: on via <mode>` when it is
live, otherwise the reason, distinguishing "you set nothing" from "what you set
is unavailable". Previously a working read path was told from a dead one by the
absence of a complaint.

The README had pointed the other way, naming `AEGIS_EXTRACT_REGISTRY` — the one
prerequisite that is now optional, since the vocabulary can be read from the
server — and never the mandatory one. Corrected.

## Operator notes

- **No migration.** No new file in the data directory, no format change, nothing
  to run against an existing store. `.aegisdb/` appears in your *project*, not in
  the server's data directory, and only when you run `aegisdb-init`.
- **`aegisdb-init` stays idempotent and non-destructive.** Re-running makes no
  duplicate hooks; existing MCP servers, hooks and settings are preserved, and the
  `memory` MCP entry is overwritten only with `--force`.
- **An explicit `--dir` now beats `CLAUDE_PROJECT_DIR`.** Running
  `aegisdb-init --dir other/` from inside a Claude Code session used to resolve
  the root to the *session's* project and pin that project's namespace into
  `other/.aegisdb/config.json` — after which `other` read and wrote another
  project's memories. Unpinned this would have self-corrected on the next run;
  pinning is what would have made it permanent. If you scaffolded another
  directory this way, check the `namespace` in its `config.json`.
- **The read path needs a model backend.** `AEGIS_ASK_PATTERN` and
  `AEGIS_ASK_VERBALIZE` both require `AEGIS_EXTRACT_MODE` set to a working
  backend (`claude-code`, `anthropic`, `openai`). They are legitimately inert
  without one — the server now says so instead of leaving you to infer it.
- **Server operators have nothing to do.** The image at this tag is v0.8.0's
  server. Upgrade it or don't; `uvx aegisdb-mcp` picks up the integration either
  way.
