# AegisDB v0.9.1 — three ways setup lied, and the checks that catch them 🔎

**Integration-only.** The server, the wire protocol and the on-disk format are
v0.9.0's; the image is republished at this tag carrying the same code. Everything
here is `aegisdb-mcp`.

All three fixes came from one exercise: running `/aegis-setup` end to end for the
first time and then using what it wrote. Each is a case of the setup looking
finished while something underneath was wrong — which is the failure mode this
integration is most prone to, and the one `aegisdb-doctor` exists for.

## The doctor now runs the recall hook

It used to check that `settings.json` *names* the hooks. Wired and working are
different things: a hook whose command cannot start fails inside Claude Code with
no error in the transcript, no log, and every file-based check still green.

```text
✓ hooks       recall + capture wired in .claude/settings.json
✗ hook runs   the recall hook exits 1 — it is wired, and it does nothing in a session
              → it printed nothing at all — the signature of a launcher that cannot
                start the command rather than a command that ran and failed…
```

Both hooks are contracted to exit 0 always ("memory is best-effort and must never
block a turn"), so a non-zero exit is unambiguous: the command did not run,
rather than ran and found nothing. Only **recall** is executed — it reads, while
capture writes, and a diagnostic must not store a memory to prove that storing
works. A timeout is a warning rather than a failure, since a first `uvx` fetch is
legitimately slow.

## Fixed: the doctor called a correctly wired project unwired

**If you ran `aegisdb-doctor` on v0.9.0 and it told you your hooks were missing,
this is why — and do not follow the advice it gave.**

The check matched only the packaged console script (`aegisdb-recall-hook`), so
the other documented wiring — `python3 "$CLAUDE_PROJECT_DIR/…/hooks/recall_hook.py"`,
which a checkout uses — was reported as not wired at all. Its suggested fix made
it worse: `aegisdb-init` would have added the console-script hooks *beside* the
working ones, and the project would then recall twice into every turn and capture
every session twice.

If you did that, remove the duplicate from `.claude/settings.json`: keep one
`UserPromptSubmit` hook and one `SessionEnd` hook, whichever form you actually
use. Both are supported and both are now recognised.

## Fixed: "default" was taken as a namespace

Asked for a namespace during setup, answering **"default"** — meaning *the*
default — pinned exactly that:

```json
{ "namespace": "default" }
```

Which is a real, shared namespace. Every project answering that way lands in one
memory store, reading and writing each other's memories: the isolation the
derived `basename+hash` name exists to provide, lost silently.

`aegisdb-init` now warns when a namespace is one of the words people use to mean
"the default" (`default`, `derived`, `derive`, `auto`, `none`, `blank`), naming
what it would have derived instead. **Warned, not rewritten** — a namespace is a
deliberate choice, and quietly substituting another would be its own surprise.
The setup skill now omits the flag for such an answer instead of passing the word
through, which is where the bug entered.

## Operator notes

- **Check your namespace if you set one during setup.** A project pinned to
  `default` shares a store with any other project that did the same. It is in
  `.aegisdb/config.json`; changing it starts a fresh, isolated memory rather than
  moving what is already stored — the records stay under the old namespace.
- **Check for duplicate hooks** if v0.9.0's doctor sent you back to
  `aegisdb-init` (see above).
- **The doctor spawns a process now.** `aegisdb-doctor` runs your recall hook
  with a probe event; it is read-only, and `--no-write` still skips only the
  save/search/delete round trip.
- **No migration, no format change, nothing to run.**
