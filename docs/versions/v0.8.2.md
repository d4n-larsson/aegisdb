# AegisDB v0.8.2 — a revised memory is recalled by what it says now 🔁

**`update` can change a record's vectors, and until now it could not.** The
operation accepted an `embedding` on the wire and threw it away: the field was
never read, and `UpdatePatch` had no slot for one. A record kept the vector it
was inserted with for as long as it existed.

Two consequences, and the quiet one is the reason this is a patch worth taking:

- **A supplied vector was silently dropped** — the same silent no-op on a
  correctly spelled field that `update` refuses outright for `fact` and
  `derivation`.
- **Editing `data` left a stale vector**, so semantic search went on ranking the
  record by prose it no longer held. Revise *"prefers espresso"* to *"prefers
  filter coffee"* and a search for espresso still found it, scored as though
  nothing had changed.

That reached the Claude Code integration directly: `memory_update` has always
computed an embedding on every text edit, and the server was discarding it. A
revised memory kept being recalled by its old meaning. **No client change is
needed** — the integration's existing behaviour simply starts working.

## What changed

`update` now takes vectors in exactly the shapes `insert` takes — `embedding`
for the single-vector case, `embeddings` for multi-vector — and the semantic
index moves with them, so the record is found where its new vector puts it
rather than where its old one did.

```json
{ "operation": "update", "id": 42,
  "data": "User prefers filter coffee",
  "embedding": [0.1, 0.2, "…"] }
```

Three cases, and the difference between the last two is the design decision:

| | |
|---|---|
| a non-empty vector | replaces what the record had, and re-indexes |
| `null` or `[]` | **clears**: the record leaves vector search and stays readable by id, tags and lexical query |
| omitted | leaves the vectors untouched |

Clearing exists so that prose a caller cannot re-embed can stop claiming a
meaning it no longer has. Omission cannot be read as "clear" precisely because
an edit to tags or confidence must not cost a record its place in recall.

Sending both keys clears only if *both* say so: `{"embedding": null,
"embeddings": [[…]]}` sets the multi-vector rather than discarding it.

**A malformed value is refused.** Unlike `insert`, which reads any non-array as
"no vector", `update` rejects a value that is neither an array nor `null`. The
shapes are identical but the stakes are not: on an insert a stringified vector
or a stray scalar costs a new record its index entry, while on an update it
would delete the vector the record already holds — and answer `ok`.

## Also fixed: a cleared vector came back after a crash

Recovery re-adds vectors for records in the log tail and skipped those without
one, so a version that cleared its vector left the checkpoint's copy in the
index — and `semantic_index_reconcile` does not evict it, because the record is
still live. After an unclean restart the record ranked by a vector it did not
hold: the exact failure clearing exists to prevent, on a routine 60-second
checkpoint cadence. The tail pass now evicts.

This is reachable only through the clear path above, so it has never affected a
released version. It is called out because the shape of the bug — an index that
disagrees with the record after a crash — is worth recognising.

## Operator notes

- **No migration, no format change, nothing to run.** Upgrade in place.
- **Records edited before this release still carry their original vectors.**
  Nothing rewrites them: the log holds what it holds. To correct one, send an
  `update` with a fresh `embedding` (or `null` to drop it) — for the Claude Code
  integration, one `memory_update` with the text re-sent is enough.
- **`insert` is unchanged**, including its lenient reading of a malformed
  vector. Tightening it is a behavioural change to a shipped operation and is
  not in a patch release; the asymmetry is documented at both call sites.
- **A failed re-index is now logged.** `semantic_index_add` drops a record's
  prior slots before adding the new ones, so a failure leaves an existing record
  with neither vector while the log already holds the new one. That is a hole in
  recall only a restart repairs, and it used to be silent. Watch for
  `update: record <id> is out of the semantic index until the next restart`.
