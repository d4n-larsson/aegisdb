# AegisDB v0.8.3 — a release you can read the status of 🚦

**No functional change.** The server, the wire protocol, the on-disk format and
all three Python packages are v0.8.2's code, republished under a new version.
Nothing here needs upgrading to; if you are on v0.8.2 you already have every
behaviour this release contains.

It exists for one reason: **v0.8.2 published correctly and reported failure**,
and that is not a state to leave a release in.

## What happened to v0.8.2

A single `git push origin v0.8.2` fired the PyPI workflow twice, three seconds
apart. With no concurrency group both runs proceeded, and because the three
package jobs are independent they raced per package and split the release:

| job | run A | run B |
|---|---|---|
| `aegisdb-mcp` | **success** | failure |
| `aegisdb` (client SDK) | failure | **success** |
| `aegisdb-langgraph` | failure | **success** |

Every package reached PyPI exactly once, so v0.8.2 is complete and correct. But
both runs report failure, each having lost the race for what the other won — and
from the status alone you cannot tell whether anything published at all. The
image and the GitHub Release were unaffected; `docker.yml` already had a
concurrency group and cancelled its own duplicate.

## The fix

- **A concurrency group per tag** on the PyPI workflow, so a duplicate waits
  rather than races. `cancel-in-progress: false`, unlike every other workflow in
  the repo: cancelling a publish mid-upload is exactly the partial release the
  group exists to prevent.
- **`skip-existing: true`** on all three publish steps, so the duplicate that
  now waits its turn finishes green instead of failing on files the first run
  uploaded. PyPI uploads are immutable, so re-uploading a version can only be a
  no-op — the one thing it must not do is fail a release that is already out.

Neither changes what a first, uncontended publish does. This tag is also the
first real exercise of both.

## Operator notes

- **Nothing to do.** No migration, no format change, no behavioural difference
  from v0.8.2. Upgrade only if you prefer your deployed version to match a
  release whose CI is green.
- **v0.8.2 remains a valid release** and is not withdrawn. Its artifacts are
  intact on PyPI and GHCR; only its workflow status is misleading.
- The interesting release to read is still
  [v0.8.2](v0.8.2.md) — `update` gained the ability to change a record's
  vectors, so a revised memory stops being recalled by its old meaning.
